# 受眾與超白話寫作規則

super-eli5 的「超」有兩層：比一般 ELI5 更簡單（一句話、一個類比、一張圖），也比一般 ELI5 更誠實（每句話知道自己站在哪一層）。

## 六層輸出，順序固定

| 層 | 名稱 | 給誰看 | 規則 |
|---|---|---|---|
| L0 | 一句話版 | 五歲小孩、只讀第一行的主管 | 一句話、沒有術語、沒有數字以外的符號；讀完就能複述 |
| L1 | 一個類比 | 完全外行 | 一個主類比加上「類比在哪裡失真」；不寫第二個類比 |
| L2 | 三層真相 | 想懂的人 | 類比 → 技術事實 → 但要注意；技術事實用來源說話，注意事項寫真正會被誤用的地方 |
| L3 | 一張圖一個場景 | 需要看流程的人 | 每個場景 2 至 6 個節點；節點標籤是「誰在做什麼」，不是名詞堆疊 |
| L4 | 失效鏡頭與教回來 | 要負責這件事的人 | 至少一個「什麼時候會壞、你會看到什麼」；1 至 3 個能用自己的話回答的問題 |
| L5 | 證據表 | 要查證的人 | 每筆證據的等級、來源、引述、不可變識別、檢驗等級 |

聊天回覆至少要有 L0 到 L2 與 L5 的摘要；HTML artifact 會完整呈現六層。

## 受眾旋鈕

- 五歲版：只留 L0、L1；每句最多 15 個中文字；不出現任何英文縮寫。
- 主管版：L0 到 L2 加上失效鏡頭；數字要帶參照物（「比上個月多 300 人，大約一個高中的人數」）；結論先講。
- 同事版：全部六層；技術名詞保留原文，但第一次出現時附白話。

`audience` 欄位寫具體的人，不寫「一般使用者」。

## 句子規則

- 一句一個想法；主詞是人或系統的具體元件，不用「它會被處理」這種沒有主詞的被動句。
- 先圖後字：能畫成場景的流程，不用三段文字解釋。
- 數字帶參照物：百分比、時間、金額都對照讀者熟悉的東西。
- 術語第一次出現就附白話，並收進 `glossary`。
- 不用「基本上」「某種程度上」「其實很簡單」這類沒有資訊的填充語。
- 推論用推論的語氣：「應該是」「推測」「還沒確認」；已驗證用肯定句並附證據編號。
- 不寫「顯然」「大家都知道」；讀者如果真的知道，就不會來問。

## 類比規則

- 類比只負責「像什麼」，不負責「所以應該怎麼做」；結論永遠回到技術事實層。
- `analogy.limits` 必寫：類比在哪裡會誤導。找不到失真點，通常代表類比太寬鬆或太完美，換一個。
- 類比用讀者的日常：早餐店、收銀機、便利貼、通訊錄；避免需要另一個專業才能懂的類比。

## 常見術語的白話替代

| 術語 | 白話 |
|---|---|
| 去重 | 同一個人只算一次 |
| 分區 | 按日期切成一天一格 |
| 口徑 | 這個數字怎麼定義、怎麼算的規則 |
| 血緣 | 數字是從哪張表、經過哪些步驟算出來的 |
| 回補 | 把缺掉那一天的資料重新補進來 |
| 顯著 | 和「沒差」很不搭，不代表重要 |
| 快取 | 常用答案先抄一份放在手邊 |
| 冪等 | 同一件事做兩次，結果跟做一次一樣 |

## zh-TW 用語

- 繁體中文、台灣慣用詞：資料（不是數據）、程式（不是代碼）、軟體、使用者、伺服器、資料庫、佇列。
- 全形標點；中文與英數之間留一個半形空格；引號用「」。
- 英文專有名詞、欄位名、SQL 關鍵字保留原文，不硬翻。
- 使用者用 zh-CN 或英文提問時，`language` 跟著使用者，解說文字也跟著切換；UI 文字由 renderer 依 `language` 提供。

## 聊天回覆的 Markdown 模板

```markdown
## 一句話版
（L0）

## 一個類比
（L1 類比）
類比在哪裡失真：（limits）

## 三層真相
- 類比：…
- 技術事實：…（[e_xxx]）
- 但要注意：…

## 什麼時候會壞
- 壞掉的地方 → 你會看到的症狀（[e_xxx] 或「推測」）

## 教回來
1. 問題（參考答案收在 HTML 內）

## 證據
| 編號 | 等級 | 來源 | 引述 | 檢驗等級 |
```

證據表只列 L5 摘要；完整欄位放在 spec 與 HTML。
